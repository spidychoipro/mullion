# 구조

## 한 줄 요약

셸은 브라우저 UI만 그리고, 실제 웹 콘텐츠는 엔진 어댑터 뒤에 숨긴다. 셸은 어댑터가 Chromium인지 Gecko인지 모른다.

## 레이어

```
┌──────────────────────────────────────────┐
│ shell        창, 사이드바, 스페이스, 분할 뷰, 커맨드바 │
├──────────────────────────────────────────┤
│ tab model    탭/스페이스 상태, 히스토리, 세션 복원      │
├──────────────────────────────────────────┤
│ engine api   createTab / navigate / snapshot / ... │
├────────────────────┬─────────────────────┤
│ adapter: chromium  │ adapter: gecko      │
│ (CEF 또는 WebView2) │ (Gecko embed)       │
└────────────────────┴─────────────────────┘
```

핵심은 `engine api` 경계다. 어댑터는 다음만 노출한다.

- `createView(url) -> viewId` : 콘텐츠 영역 생성
- `attach(viewId, rect)` : 셸 창 안의 좌표에 붙이기
- `navigate(viewId, url)`, `back/forward/reload`
- `snapshot(viewId)` : 탭 미리보기용 캡처
- `history/favicon/title` 이벤트
- `suspend(viewId)` : 안 보는 탭의 리소스 회수

이 목록을 최소로 유지하는 게 목적이다. 엔진별 기능 차이는 어댑터 안에서 흡수하고, 셸에는 새지 않게 한다.

## 엔진 선택지

| 엔진 | 임베딩 | 장점 | 단점 |
| --- | --- | --- | --- |
| Chromium | CEF | 성숙함, 확장 지원, 문서 많음 | 바이너리 큼, 업데이트 직접 관리 |
| Chromium | WebView2 | 윈도우에 이미 있음, 배포 가벼움 | 오프라인 스냅샷/버전 고정 어려움, 확장 불가 |
| Gecko | gecko embed | 파이어폭스 엔진, 확장 생태계 | 임베딩 문서 거의 없음, 빌드 무거움 |

윈도우 우선이면 1차 목표는 CEF다. WebView2는 "가볍게 체험" 모드로 두고, Gecko는 별도 트랙으로 분리한다.

## 셸 스택 후보

- Electron + CEF 네이티브 모듈: UI 생산성 높음, CEF 연동은 직접 붙여야 함
- Tauri(Rust) + wry: 가볍지만 멀티 엔진 임베딩은 직접 구현
- 순수 C++/Rust 셸: 자유도 최고, UI 개발 속도 최악

결정 기준은 "탭마다 다른 엔진을 붙일 수 있는가"다. 이걸 못 하면 지금 단계에서 후보에서 뺀다.

## 미결 사항

- 셸 스택 확정 (Electron vs Tauri vs 네이티브)
- CEF 배포/업데이트 전략 (자체 빌드 vs Spotify 빌드)
- 스페이스 데이터 저장 형식 (SQLite + 이벤트 로그?)
- 탭 suspend 정책 (N개 이상 / M분 이상 비활성)
- Gecko 임베딩 실현 가능성 검증 스파이크
